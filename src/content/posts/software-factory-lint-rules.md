  <p class="lede">从需求、实现、验证、审查到发布，哪些判断可以写成自动检查，哪些仍要人来做。</p>
  <p>软件写得越快，人就越来越看不过来。于是问题会变得很具体：哪些判断可以写成反复执行的检查，哪些仍然必须由人来做。这里说的软件工厂，不是一座不必看代码、也不必开灯的黑箱，而是一条能把重复判断做成检查、又能把关键判断留给人的工程流程。</p>
  <p>本文对照三份材料来讨论这件事。第一份是 Lauren Tan（@poteto）的演讲《All Code Is Slop (Except Mine)》。第二份是 Claude Code 团队的《How the Claude Code team does code review》，作者是 Addy Osmani、Morgan Westlee Lunt 和 Qing Wang。第三份是 Matt Pocock 与 Mario Zechner、Armin Ronacher 的对谈整理。</p>
  <p>三份材料面对的是同一类压力：agent 产出变快之后，怎样避免质量跟着一起垮掉。可他们给出的并不是同一套规范。后文是综合建议，不是三方已经统一的标准。</p>
  <h2>他们各自在说什么</h2>
  <h3>Lauren Tan：先改代码和检查，再扩大自动化</h3>
  <p>Tan 把问题说成信任，但不是盲目信任。官方阅读稿里的概括是：要在 agent 所处的环境上下功夫，才能相信它们会做对的事。她用一座倒金字塔来安排投入。最宽的一层是代码库本身，也就是好的 API 设计、架构和重构；接着是静态分析，包括 lint、类型检查、编译器和测试。再往下是运行时验证和形式化验证，用来问两件更深入的事：重要性质是否仍然成立，以及行为是否符合这次请求。最窄的一层才是书面规则、技能和 <code>AGENTS.md</code>，留给仍然需要判断的事情。越靠近人审，成本越高。</p>
  <p>她特别强调，代码库是 agent 看到的最大输入之一。仓库里若留下权宜之计，下一个 agent 完全有理由把它当成既有做法；每多一份拷贝，这种做法就更像常规。因此，清理过时代码并不只是在还历史债，而是在改变 agent 接下来会学到什么。一条反复出现的审查意见，应当变成确定性的检查。</p>
  <p>她举的例子把这条原则落到了很窄的地方。Grok Bot 团队的客户端框架 Dune，把 React 的 <code>useEffect</code> 限制在选定的框架接口里，并禁止用在普通产品代码中。这并不是断言这个钩子永远不该用，而是承认它需要细微判断，不适合作为产品代码的默认选择。框架作者仍然可以在受支持的路径里实现必要行为，审查新产品功能的人也就不必每次重新判断该不该破例。另一个例子是 Electron 的进程边界：目录被明确分成 <code>electron-renderer</code> 和 <code>electron-main</code>，依赖分析和 lint 禁止错误方向的引用。目录名给 agent 提示，检查则在它没看懂提示时仍然拦住。</p>
  <p>她还谈到，注释可能把权宜之计保存下来。在她举的计时器例子里，agent 用 <code>setTimeout</code> 一类做法补上架构冲突，又用注释解释这次这样做是合理的。于是下一份改动就会把这种补丁看成有意设计。注释会过期，人也常常不读，而且它无法阻止下一次再犯。Grok Bot 和 Dune 因此把指导放进 lint 报错里，让 agent 在违规当时看到该修的根因。官方阅读稿里的顺序是：先加 lint，挡住新的实例；再清理旧例子，免得被继续复制；然后给 agent 一条能够验证行为的路径。如果内层的修改和检查循环本身就不稳，再把外层自动化放大，只会把修修补补的成本一起放大。</p>
  <h3>Claude Code 团队：检查要分层，人的时间要用在人才能判断的事上</h3>
  <p>官方文章一开始就把代码审查分成两件事。一件是在发布前发现并修好问题，另一件是在团队里建立对代码库的共享理解。他们不再把「有没有人读过这行代码」当成充分标准，而改问：这次改动可能在哪里出错，哪一种检查——自动的还是人的——最适合抓住它。</p>
  <p>他们把人的时间看成稀缺资源，而且这份时间有两头：人花在审查上的时间，以及人花在修复坏代码所引发问题上的时间。如果只减少前一头，后一头跟着涨上来，就没有真正省下时间。他们用回滚率和事故率作为护栏：这两项如果上升，说明时间只是被转移了，并没有被节省。</p>
  <p>在流程上，多数审查发生在打开 pull request 之前。他们让 Claude 跑得起来测试、构建，或者拿截图去对照设计，并要求它出示输出，而不是口头说做完了。然后用一个处在新上下文里的子 agent 再看一遍 diff。Boris Cherny 认为，给 Claude 一条能够验收自己工作的路径，大概是出好结果最重要的事。当自动审查器反复标出同一类问题，他们就在源头修改：改技能、加 lint，或者更新 <code>CLAUDE.md</code>、<code>REVIEW.md</code> 这类说明。</p>
  <p>他们对 <code>REVIEW.md</code> 的要求很具体，因此很适合当作规则写法的参照。好的说明要短，并写出在这个仓库里失败长什么样，例如文档是「它在说谎」，配置是「它把请求送错了地方」。说明还应限制琐碎意见，列出可以跳过的路径，并要求给出文件和行号作为证据，而不是凭名字猜测。如果没有要修的问题，也要直说。他们还会另外检查审查器是否真的遵守这些说明。</p>
  <p>每一条发现都必须被回应：修好，或者说明理由后关闭。安全审查是独立的一层，未解决的发现会挡住合并。他们同时强调，审查必须收敛，因为一个作为作者的 agent 和一个作为审查者的 agent，可能无限地互相打转。他们后来给轮次设了上限，并在前几轮之后只再看新增的 diff，还要求按问题类别一并修复，而不是只改被点到的那一行。他们通过观察人们对评论做了什么来衡量噪声：是修了、说它错了、说这是有意行为，还是觉得不重要。他们写下的优先级是：先抓住真问题，其次才是减少审查轮次。</p>
  <p>人仍然留在回路里，但位置更窄。人要决定要不要做这件事，要审查高风险代码，要审查会被别人复制的架构，要阅读测试输出和截图这类证据，还要为上线结果承担责任。风险等级由改动本身决定，而不是由作者是谁决定。机器人的批准不能填补「必须由人批准」的空位。机器承担了大部分阅读之后，他们用 explainer 补人对某一块代码的理解，而不是指望每个人靠读琐碎 diff 来维持全局印象。</p>
  <h3>Pi 对谈：测试通过，并不等于系统是对的</h3>
  <p>在已发布的对谈笔记里，Mario Zechner 和 Armin Ronacher 并没有反对检查本身。他们担心的是另一种自我安慰：只要 agent 写了一大堆检查规则和测试，系统就一定是好的。模型仍会追着眼前的目标走，仍可能量错对象，或者量得不够。单个模块都通过，也不等于这些模块组合起来仍然通过。因此，有验证总比没有好，但不能因为测试是绿的，或者磁盘上放着一堆证明代码，就获得安全感。</p>
  <p>Mario 把再用一层模型来审查，称作防止自己偷懒的保险，而不把它叫做安全。不同模型往往会给出不同判断，这有帮助；可如果把它们调得很苛刻，它们又会过度报问题。最后仍要靠人来筛选。笔记里还写到，模型被大量「最佳实践」训练过，其中不少其实可能加重系统负担，例如到处做防御性检查。若放任这条路走下去，系统会明显变复杂。多出来的保护有时会让人误以为已经安全，却漏掉真正重要的缺口。</p>
  <p>Armin 举过一份过期文档的例子。agent 很愿意维护写着「发现」的说明，其中一份在数据库还空着时写下「只有 2000 条记录」，后来记录已经到了数百万条，权衡也就完全不同了。文档没有写清自己成立的条件，过期之后就会把人带偏。出了问题，承担责任的仍然是人。</p>
  <p>他们也谈到，理解本身不能被流程省掉。笔记里写到，他们听过同行在事故会上的情形：没人知道发生了什么，所有人都在问自己的模型。Mario 认为这非常可怕。和人交谈、真正体会用户需要什么，可能比埋头写代码更能保住价值。至于一座自己运转、不必看代码也不必开灯的软件工厂，他说，如果它既做得出，又有经济价值，它就会存在；而他还没有看到它存在。若没有经济价值，那就只是自娱。这些都是现场判断，不是对照实验的结论，但和前两份材料一样，都认为检查不能替代人对系统和用户的理解。</p>
  <h2>从需求到发布，哪些可以自动查，哪些必须由人判断</h2>
  <p>把三条线索放到同一条流水线上看，分工会更清楚。以下是综合建议，不是任何一位原作者已经画出的流程图。</p>
  <p>在需求阶段，能够自动检查的，多半是这次改动有没有写出可验收的条件：例如是否说明要验证哪一条用户路径，是否附上对照用的截图、测试或命令。不能自动代替的，是要不要做这件事，以及用户真正需要的是什么。Claude Code 团队把「应不应该做」明确留给人；对谈笔记里同样把和用户交谈、体会需求，看成更难被机器代替的工作。</p>
  <p>在实现阶段，能够自动检查的，是已经反复出现、并且能把边界说清楚的错误：错误的依赖方向、不该出现在产品代码里的接口、以及把权宜之计复制成常规的写法。更有效的做法，常常不是再写一条警告，而是先改 API，让错误的选择根本写不出来。仍然需要人的，是系统设计、接口取舍，以及会随数据体量变化的权衡。这些条件会改变，因此也不该假定有一段提示词能永远自动做对。</p>
  <p>在验证阶段，能够自动检查的，是行为有没有被实际跑过，以及关键性质在这次运行里有没有被破坏。Tan 强调要让 agent 跑起来真实应用，并用功能地图和可复用的命令来产生截图或录像，作为证据。Claude Code 团队也要求模型出示输出，而不是自称完成。必须由人判断的，是这些检查到底有没有量对东西，以及一次成功路径能不能代表系统在其他组合下仍然成立。绿的流水线只能证明，你想到去查的那些事通过了。</p>
  <p>在审查阶段，能够自动检查的，是常规缺陷、安全问题，以及说明文件里已经写清「失败长什么样」的约定。必须由人做的，是阅读证据、判断某种架构会不会成为别人复制的模板，以及为结果签字。审查意见如果又多又苛刻，人还可以很快略过；agent 却往往会照单全改，于是引出新的提交和新一轮审查。所以规则不仅要能抓住问题，还要能控制误报，并让审查在有限轮次里结束。</p>
  <p>在发布阶段，能够自动检查的，是构建、测试、合并队列，以及是否写了如何回退。必须由人承担的，是上线后果，以及事故之后的回看：哪一层本该抓住它，是规则写错了、过期了，还是这件事本来就不该只交给检查。</p>
  <h2>一条可用的规则，至少要写清这些</h2>
  <p>综合建议是：软件工厂里的 lint rule，不该只是代码风格清单。它更像一份带条件的检查契约。下面这个模板，用来把反复出现的审查意见写成可执行、可维护的规则。它不是 Tan 或 Claude Code 团队公布的格式。</p>
  <div class="rule">
    <p class="rule-title">建议中的规则字段</p>
    <ul>
      <li>要挡住的失败：用一句话说清这条规则在拦什么。</li>
      <li>适用条件：它在哪些目录、哪些改动类型、哪些数据规模下成立。条件本身也要写进说明里，避免以后环境变了，旧规则还在把人带偏。</li>
      <li>证据：报错必须落到文件和行号，或者落到一条可复现的命令及其输出，而不能只凭函数名猜测。</li>
      <li>严重程度：是挡住合并，还是标为次要问题，或只是提示。风格和清理类意见，不应默认获得和缺陷同样的阻断力。</li>
      <li>例外：什么情况下可以不适用，谁有权确认例外，例外是否必须附理由并到期复查。</li>
      <li>报错文本：直接指向该修的根因，而不是只写「出现了违规」。如果正确做法是改用某个 API，就把这条路写进报错。</li>
      <li>失效和维护：这条规则依据什么假设；假设失效时如何发现、由谁修订或下线。如果自动审查器开始反复误报，就应回到源头改规则，而不是靠人一次次关闭工单。</li>
    </ul>
  </div>
  <p>举一个建议性的例子，只为说明写法。假设产品代码不该直接使用某个需要大量临场判断的接口，而应调用框架提供的封装。适用条件可以写成「仅对产品目录生效，框架实现目录除外」。证据是具体的引用位置。严重程度是合并前必须处理。例外需要框架维护者确认，并写明理由。报错应说明：请改用框架提供的路径；如果现有路径不够用，应先扩展框架，而不是在产品代码里打补丁。维护条件则是：框架路径覆盖这类需求后，例外就必须收回；规则若把合法的框架改动也拦住，就应收窄匹配范围，而不是让团队习惯性关闭报错。</p>
  <p>这样写，是为了避开三种常见负担：防御性检查把系统堆复杂，重要缺口反而看不清；误报过多，审查无法收敛；规则和文档过期，还继续指导人和模型。Tan 的办法是先改设计或加可执行检查，再清理旧例子。Claude Code 团队的办法是观察人们对每条意见做了什么，并用事故反向充实检查。对谈笔记则提醒：写规则时要把成立条件写清，不要让过期说明把后来的人带偏。</p>
  <h2>规则要保护的，是理解和判断</h2>
  <p>如果规则只服务于更快地自动合并，流程也许能转起来，却可能把理解一起转没。Claude Code 团队仍然要人阅读证据，并明确为结果负责。对谈笔记里写到，Mario 在涉及工具机制和 agent 循环等核心部分时，仍然自己读改动；也正因为他还在读这些修复，才继续了解代码库。自动检查越强，人越需要知道这些检查会漏掉什么。如果说不清这一点，就不该把一次快速批准当成审查已经完成。</p>
  <p>因此，软件工厂里的 lint rule 首先该回答的，不是代码好不好看，而是：从需求到发布，哪些失败已经能被自动抓住，哪些判断仍然要人做出，以及一条规则在过期或误报时怎样被修正。能写成检查的，就不要让人反复看同一类错误；不能写成检查的，就不要假装测试通过等于事情已经做对。先把这一层内循环做稳，再去放大外层的自动化。否则，工厂只会更快地复制同一类问题。</p>
