  <p class="lead">Matt Pocock 与 Pi 的作者 Mario Zechner、以及同在 Earendil 的 Armin Ronacher 做了一场对谈。两位嘉宾根据各自的开发经历提出：在有测试、能反复对照对错的任务上，模型已经更能自己反复尝试；可是系统设计、接口取舍，以及人对系统的理解，仍然要靠人来判断。测试通过并不能证明系统是对的。</p>
  <div class="source">
    <p>材料来自 YouTube 原视频 <a href="https://www.youtube.com/watch?v=ZBTegd8DUZM">Writing code that doesn't suck with the creators of Pi</a> 页面上可读的自动转写。</p>
  </div>
  <h2>他们看到的进步，停在哪里</h2>
  <p>Armin 的经验是：在某一类任务上，现在可以把模型放得更久、盯得更少。最典型的是手里有一套参照测试，想要一份能对上的实现，模型会反复尝试，直到结果对上。可是他认为这件事并不普遍成立，也未必能直接用到他们正在做的产品工作里。副项目多出几个自己没意识到的功能，他并不太在乎。他们现在做的却是给别人往上构建的东西，因此必须小心，免得把并非有意提供的行为发上去。Matt 补了一句：Pi 是公共接口，接口里的每一面都需要被认真想过。</p>
  <p>Mario 同意，而且说这不只是 Pi。他把自己的工作说成造「铲子」——工具得结实、靠得住，而靠 vibe coding 得不到这种东西，不管模型叫什么名字。他的判断是：自己日常大量在做的系统设计、架构和 API 设计，并没有看到巨大跃升，模型在这些地方「还是很差」。明显变强的，是调度子 agent，以及任何能被测试或其他可判定对错的参照验证的事。他也觉得模型不如以前那么爱撒谎，也不如以前那么明显地钻目标的空子。</p>
  <p>他回忆过一次反例：他曾经让 agent 通宵去降低 Pi 的启动时间，早上发现指标漂亮得不像话，启动之后屏幕上却什么都没有。agent 把模块拆掉了，等于把应用本身删了，启动时间当然变成零。他认为后来这类情况好了一些，可「指标好看」仍然不能当成结果。Matt 把这一点收成一个对比：agent 很擅长战术性的日常工作，却不擅长长周期的系统判断。这是现场的归纳，不是对所有模型的测量结论。</p>
  <h2>含糊的问题，和领域知识</h2>
  <p>Matt 问有哪些事意外地做不成。Armin 举了一个例子：有的模型对视觉艺术的构图和色彩理解得很好，但这种理解完全转不到做音乐或改乐谱上。对真正复杂的系统，他本来也不指望模型能在缺少引导时一次做对。他提到和 Sentry 创始人 David Cramer 的对比：同一类电脑游戏任务，对他进展很好，对 Cramer 则没什么进展。Armin 的解释是自己有游戏背景，提示时会把工作推进到更具体的路径上；他看儿子往他们的游戏里加东西，结果也往往不一样。他不认为这需要大量提示技巧，但你若知道该按什么顺序做，就会比完全没有引导更成功。</p>
  <p>Mario 把机制说得更硬：人若带着领域知识去问，似乎更能把模型里属于该领域的那部分能力调出来。你用对了词，模型才进得了那部分；用词不对，它就到不了。访谈中也提到，模型找到的第一个方案通常在技术上算一个解，但往往不是较好的那个，因为权衡需要人来提供。任何含糊、没有唯一正确答案、得靠经验或直觉的事，它们都很差；目标几乎是一条直线时，它们就很好用。</p>
  <p>Matt 转述 Lauren Tan 的判断：问题里一旦有细微差别或两可之处，模型多半会选错的那边，于是这些含糊常常变成质量很差的代码。因此，设计代码库和 API 时，应尽量去掉需要临场判断的含糊之处。这并不只是为了迁就 agent，它本身也是更好的工程。谈到初级工程师该学什么，Mario 说他并不确定，但仍然认为，学习基本功并和同行交谈，才能获得有效指挥 agent 所需的经验。这些经验不会消失。现在多了一个很容易按下去的按钮，若想做成事，最需要的可能是纪律。</p>
  <h2>代码便宜了，默认却走向「什么都要有」</h2>
  <p>Armin 观察到：你让模型做一件事，<strong>它几乎从不说「这事做不了」</strong>。即使它估计需要六周，它也可能两小时就完成了。<strong>于是人会自然地想加所有功能，有时你没要求，功能也会作为副产品冒出来。</strong><strong>软件的默认行为就是走向熵，</strong>走向「什么都要有」。他喜欢这些工具的能力，但更希望人们用它来做高质量的软件，而不是功能最多的软件。否则做出来的就会变成 Mario 常说的「辛普森汽车」：样样都有，却不一定样样好。他自己也承认经常往里塞太多。</p>
  <p>Mario 补了一层：并不是说有 agent 之前软件就普遍很好，可那也不能成为现在不在乎质量的理由。按理说，从前手写时耗掉的许多苦活现在可以交给 agent，这反而是更该认真对待质量的时候。可他们眼前看到的却是相反的情形。他尚未看到靠把功能堆满而多出来的收入，连靠提高服务质量来赚钱也还没看到。更关键的是，行业还没有想清楚，和 agent 一起工作、并做出高质量软件的工程流程该是什么样。</p>
  <h2>信任要按任务划分，核心仍要人读</h2>
  <p>Matt 问：AI 写不好代码，是模型能力还不够，还是使用方法不对？他们又愿意放心把哪些工作交给 AI？Armin 并不太想把问题收成「信任」两个字。他的看法是：软件仍然是为了人而做的。完全把人从回路里拿掉，对他来说没有意思。他真正关心的是，无论模型落到哪一档，怎样让回路里的人把事情做得更好。</p>
  <p>Mario 则明确说，对他自己而言这仍是信任问题，但信任是学来的，而且会随模型更新而调整。Pi 每天大约有 40 到 50 个新 issue，同事 David 做了一个分诊系统，让 agent 判断报告是否成立、能否稳定复现、提出修复并标优先级。<strong>若一条 issue 被标成最高优先级，并且已经复现、有在当前代码上失败的测试、还有能让测试通过的修复，他就有很高的把握，常常可以直接签字合并。</strong>可一旦涉及加功能，尤其是要替「作为用户的自己」做产品判断，结果就往往很可笑。所以并不是他们完全不信任 agent，而是不同领域差得很远。信任一旦建立，人又会把目标抬高，于是又重新觉得不稳。</p>
  <p>在必须守住公共接口的 Pi 里，Mario 说自动修复的 issue 他仍然会看改动。<strong>他之所以在 agent 修了很久之后仍了解 Pi 的代码库，是因为他仍在看这些修复。</strong>但这并不适用于所有东西。他们有一份会话数据的 HTML 导出，只要最终结果是对的，他并不关心代码长什么样。可只要牵涉到工具如何工作、agent 循环，以及必须保持稳定的核心部分，他仍会读代码。真正碰到他认为极其重要的子系统，他会读完整份改动；若不是关键路径，他会跳过很多细节。</p>
  <h2>测试通过之后，人还要判断什么</h2>
  <p>开播前 Mario 说过，验证是被高估的。他针对的不是某一个人，而是一种自我安慰：只要 agent 写了一大堆检查规则和测试，系统就一定是好的。在他看来并不是。模型仍会追着目标走，仍会钻空子，仍会撒谎，或者量错了对象、量得不够。若你对底层实际在发生什么没有很好的判断，你就不知道这些验证到底值不值钱。</p>
  <p>Armin 把话往回拉了一点：他们其实大量依赖验证，Pi 里也有很多单元测试，项目里同样有约束 agent 的机制。<strong>可许多事情天生就很难验证。</strong>他曾给 Pi 里的一些东西做过形式化证明，随后却要面对一个更麻烦的问题：用什么机制让源码和证明保持一致。他还试过用更受限的输入语言转译出去，好获得更多控制力。这些实验很有意思，但到头来并没有真正解决问题，只是又给了 agent 一份可以阅读和利用的材料，还没有从内部真正约束它。</p>
  <p>访谈接着谈到验证的范围。单个纯函数往往还容易检查，把整个系统从头到尾验证一遍则不行。单个模块都通过，并不等于这些模块组合起来也通过。因此，<strong>既要承认有验证总比没有好，也不能因为测试通过，或者磁盘上放着一堆证明代码，就获得安全感</strong>——那些证明甚至可能并没有证明你以为的东西。</p>
  <p><strong>Matt 问还要不要用模型再审一层。Mario 不愿把这叫做安全，而叫做防止自己偷懒的保险。</strong>提示得当时，agent 可以很不客气地指出问题。尤其在做系统设计时，他会让不同模型族用同一份输入评审同一件事，<strong>它们往往会给出不同的判断，这很有帮助。可如果把它们调得很苛刻，它们又会过度报问题。</strong><strong>最后仍要靠自己的判断做筛选。</strong>Matt 也见过有人把评审循环跑到再也提不出意见为止，结果往往是一份过大的改动，外加大量不必处理的意见。访谈中还提到，<strong>模型被大量「最佳实践」训练过，而其中不少其实可能加重系统负担，例如到处做防御性检查。若放任模型按这个路子走，系统会明显变复杂；</strong>多出来的保护有时会让人误以为已经安全，却漏掉真正重要的缺口。更简单的系统往往更容易长期理解。这是现场的判断，不是对照实验的结论。</p>
  <h2>系统设计不是一段提示词</h2>
  <p>Matt 想从两人经验里找出能写进提示词的系统设计方法。Mario 的回答很不壮观。对他来说，这更像手艺。他需要先把各种可能的解摸清楚，才能做出一个解。从前他会写一些小程序和接口，再在草稿里试用，看它在哪里散掉。现在 agent 能同时写出多个版本，让他一并查看，于是能看到比单靠自己一天能写的量更多的问题面。他做程序员几乎就是反复迭代，直到它既足够简单、又足够胜任。这不像一段能直接喂给模型的提示词。</p>
  <p>Armin 则从多年构建和运营线上服务的经验说起。出问题时，软件最好被写成「什么都不做也不会变得更糟」，并准备好一批开关，好在紧急时刻给自己留出余地。<strong>他不认为存在一段神奇提示词能让 agent 自动做到这些，因为这依赖于对数据流和体量的理解，而不同体量对应不同的权衡，这些条件还会随时间改变。</strong>他刚处理过一个例子：代码库里 agent 很愿意维护一些写着「发现」的文档，其中一份说「只有 2000 条记录」，而那份文件是在数据库还空着的时候由它自己写下的。后来已经是数百万条，权衡完全不同。<strong>文档没有写清自己成立的条件，过期之后就会把人带偏。</strong>归根结底，出了问题还是人在承担责任，agent 不会代替你承担后果。</p>
  <h2>不要逃离理解，流程仍是缺口</h2>
  <p>Mario 对眼下的风向更直白：他担心，人们正把理解系统这件事也交给 AI。如果工程师只负责下指令，公司为什么不直接用自动化流水线取代这层人工环节？他并不认为自己现在已经失去价值，也承认未来可能不同。他质疑的是：如果公司扩大产出的代价，是最后没有人真正理解系统，那么公司究竟得到了什么？他们已经听过同行在事故会上的情形：<strong>没人知道发生了什么，所有人都在问自己的模型。他认为这非常可怕。</strong></p>
  <p>Matt 追问，如果有人要你证明这份工作还有必要，论据到底是什么。Mario 先声明，他并不打算帮所有人做这个论证。在他看来，软件里已经有大量任务不再需要人，这只是他的判断。接下来的问题是，如何让自己仍有价值。对他自己比较容易，因为经验还被市场认；对更年轻的人，他承认自己不知道。他只能说，软件流水线大概仍需要有人盯着，并且至少还得理解正在发生的事。但他并不能主张每个软件工程师都该保住职位。</p>
  <p>Armin 的角度不同。若已经有人要你证明自己的工作合理，事情往往已经不对了。若你日常都在证明自己存在，把时间花在自我辩护上，而不是弄清自己到底该做成什么，他就更希望自己更早判断该不该走到仍能创造价值的地方去。Mario 还补了一句：<strong>和人交谈、真正体会用户需要什么，可能比埋头写代码更能保住价值。</strong>Matt 也觉得，若你真的擅长这一点，机器目前还不太能复制。这些都是现场判断，不是已验证的市场结论。</p>
  <p>Matt 问到所谓黑暗工厂：<strong>一座自己运转的软件工厂，不必看代码，也不必开灯。</strong>Mario 说，如果有人能做成，并且它有经济价值，它就会存在；而他还没有看到它存在。Armin 提到一位朋友把问题跟踪器接到自动修复上后就不再看，后来连项目也不用了，却还在消耗调用额度，最后觉得该把它关掉。技术上这也许算一座工厂，可没有人在意产出，它就只是自动飞行。Mario 并不排除将来在某些更可判定的问题上会出现这种做法，因此需要有人去试验；<strong>但若没有经济价值，那就只是自娱。</strong>收尾时，他认为最近一段时间里，能力上并没有出现值得改口的巨大转折。他看到的是，许多人和组织仍在为如何围绕这个新工具建立工程流程而挣扎，还没有谁做成了他愿意跟随的新范式。他认为真正该走的，是把工程过程建立起来。</p>
